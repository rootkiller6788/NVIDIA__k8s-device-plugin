# AGENTS.md

Guidance for AI coding agents working in this repository. Human contributors should also read
[CONTRIBUTING.md](CONTRIBUTING.md) and the [documentation site](https://nvidia.github.io/k8s-device-plugin/)
which are the source of truth.

## Project Summary

The NVIDIA device plugin for Kubernetes is a DaemonSet that advertises NVIDIA GPUs to the kubelet
via the [Kubernetes device plugin](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/)
framework, tracks GPU health, and enables GPU-backed containers. As of v0.15.0 this repository also
holds the implementation of GPU Feature Discovery (GFD), which labels nodes with GPU properties.

The repository builds several binaries, each with its own entrypoint under `cmd/`:

- `nvidia-device-plugin` — the device plugin DaemonSet itself.
- `gpu-feature-discovery` — GFD node labeller, deployable alongside the plugin or standalone.
- `mps-control-daemon` — control daemon for CUDA MPS-based GPU sharing.
- `config-manager` — applies per-node configuration selected by a node label.

Go module: `github.com/NVIDIA/k8s-device-plugin`. Configuration API types live in
`api/config/v1`.

## Repository layout

- `api/config/v1/` — the plugin configuration API types (sharing, MIG, IMEX, flags).
- `cmd/` — binary entrypoints, one directory per binary (see above).
- `internal/` — supporting packages; notably `internal/rm` (resource managers for full GPUs,
  MIG devices, and vGPU), `internal/plugin` (device plugin server implementation),
  `internal/lm` (label management for GFD), `internal/cdi` (Container Device Interface spec
  generation), and `internal/resource` (NVML-backed device discovery).
- `deployments/helm/` — Helm chart for the plugin and GFD.
- `deployments/container/` — Dockerfile for the plugin image.
- `deployments/devel/` — pinned development toolchain used by `make`.
- `docs/` — additional documentation, including `docs/cdi.md` and `docs/gpu-feature-discovery/`.
- `tests/` — end-to-end and Helm test suites; `tests/` is a separate Go module.
- `testdata/` — fixtures used by unit tests.
- `hack/` — dev and release scripts (changelog, third-party notices, release prep).
- `demo/` — runnable example manifests.

## Build, test, and lint

All standard tasks go through the Makefile. Prefer make targets over invoking tools directly
so CI and local runs stay consistent.

- `make build` / `make cmds` — compile the binaries.
- `make test` — run unit tests over `cmd/...`, `internal/...`, and `api/...` with coverage.
- `make check` — run the check suite; currently this is `make lint`.
- `make lint` — run `golangci-lint run ./...` (config in `.golangci.yml`).
- `make fmt` — apply `gofmt -s` to the codebase (writes files).
- `make goimports` — run `goimports -local github.com/NVIDIA/k8s-device-plugin` (writes files).
- `make generate` — run `go generate ./...`, which regenerates the `moq` mocks.
- `make check-modules` — tidy, verify, and vendor every module, then fail if anything changed;
  CI will fail if `go.mod`, `go.sum`, or `vendor/` are stale.
- `make third-party-notices` / `make check-third-party-notices` — regenerate and verify
  `THIRD_PARTY_NOTICES.md`; CI fails if it is out of date after a dependency change.
- `make coverage` — unit tests plus a per-function coverage report, excluding mocks.
- `make test-e2e` / `make test-helm` — Ginkgo suites that require a live Kubernetes cluster with
  real GPUs. Do not report these as passing when they were not run.

Always run `make fmt`, `make lint`, and `make test` before considering Go changes complete.

After changing a dependency, run `make check-modules` and `make check-third-party-notices` and
commit the regenerated `vendor/` tree and `THIRD_PARTY_NOTICES.md` alongside the source change.
After changing an interface that has a `//go:generate moq` directive, run `make generate` and
commit the regenerated mock.

## Coding Conventions

- Idiomatic Go, following existing patterns in `internal/` for logging, error wrapping, and
  NVML access rather than introducing new libraries.
- Comments explain **why**, not **what**. Identifier names should carry the "what."
- Keep changes scoped to the task. No drive-by refactors, speculative abstractions, or unrelated
  formatting churn — one concern per PR.
- Every `.go` file starts with the Apache-2.0 boilerplate header; match the existing header in
  neighbouring files exactly rather than inventing a variant.
- Vendor directory (`vendor/`) is checked in; run `go mod tidy`/`go mod vendor` after dependency
  changes and do not hand-edit vendored code.
- `*_mock.go` files are generated by `moq` from `//go:generate` directives; do not hand-edit them.

## Testing Conventions

- Unit tests are co-located `*_test.go` files using `testify` (`require`/`assert`), typically
  table-driven with a map of named cases and `t.Run(name, ...)`. Run via `make test`. New behavior
  needs appropriate test coverage.
- End-to-end tests under `tests/` use Ginkgo/Gomega and live in a separate Go module. They need a
  real cluster with GPUs, so treat them as unavailable unless that environment is present.
- When fixing a bug, add a regression test that fails without the fix.

## Contribution process (see `CONTRIBUTING.md`)

- For any significant change (architectural change, new feature, breaking change, non-trivial
  bug fix), an issue should exist describing the problem/proposal before implementation begins —
  check for or ask about a linked issue rather than assuming a PR alone is sufficient.
- All commits must be signed off (DCO): `git commit -s`, producing a trailing
  `Signed-off-by: Name <email>` line. DCO is a required status check. Do not fabricate a sign-off
  identity — use the configured git user's identity.
- Do not open, push to, or comment on GitHub issues/PRs without explicit user confirmation.
- Keep PR titles short and imperative; fill in the sections in
  [.github/PULL_REQUEST_TEMPLATE.md](.github/PULL_REQUEST_TEMPLATE.md), and explain motivation
  ("why"), not just restate the diff.

## Things to avoid

- Never commit credentials, API keys, tokens, passwords, kubeconfigs, or private keys.
- Do not hand-edit generated files. Run `make generate` to regenerate `moq` mocks after changing a
  mocked interface. Run `go mod tidy`/`go mod vendor` after dependency changes and do not
  hand-edit vendored code.
- Do not commit built binaries, `coverage.out`, or anything the [.gitignore](.gitignore) already
  excludes.
- Do not edit `THIRD_PARTY_NOTICES.md` by hand; regenerate it with `make third-party-notices`.
- Do not modify [GOVERNANCE.md](GOVERNANCE.md) or [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) unless
  the task is explicitly about that.
